## 4. 기본 완료 범위

우선순위는 기존 프로젝트 설명 → Thread Pool·JSON 로딩 이해와 검증 → TCP/UDP 기본 실습 → 덤프 분석이다. PNG 병렬 로딩은 기본 완료 조건에 포함하지 않는다.

### 4.1 Thread Pool 이해와 검증

- Queue·접수 상태·실패 횟수를 같은 mutex로 보호하는 이유 설명.
- Queue 확인·꺼내기는 같은 잠금 구간, Job 실행과 join은 잠금 밖에 두는 이유 확인.
- condition_variable의 조건 재검사, 접수 중단 후 남은 작업 소진, 결과·예외 전달 확인.
- Worker 1개와 여러 개에서 각 Job의 정확히 한 번 실행·완료 순서 차이 확인.
- 동시 제출·Stop 경합·예외 Job·반복 종료 확인. 테스트 코드는 사용자가 직접 작성.
- 기존 독립 테스트 결과는 과거 기록이며 현재 테스트를 다시 실행한 결과와 구분.

현재 직접 검증할 순서:

| 단계 | 관찰·실험 | 완료 판단 |
| --- | --- | --- |
| 현재 사용 경로 | Application의 Start(1) → Submit → Worker 로딩 → future 수령 → 종료 추적 | 메인·Worker의 실행 위치와 결과 수명 구분 |
| 기본 작업 분배 | Worker 1/2/4개에 유한한 Job 제출 | 각 작업 ID가 정확히 한 번 실행. 완료 순서 차이는 허용 |
| 예외 | 실패 Job과 정상 Job을 함께 접수 | 실패 횟수 집계와 후속 정상 작업 실행 |
| 종료 | 접수 직후 Stop, 종료 후 Submit, 반복 Stop | 접수된 작업 완료·join, 새 제출 거부, 종료 시 멈춤 없음 |
| 결과 전달 | promise에 값 또는 예외 저장, 메인에서 future 확인 | 준비 전 대기·확인과 준비 후 get의 차이 설명 |

테스트 코드와 프로젝트 설정은 사용자가 직접 작성한다. 테스트의 카운터·결과 수집도 경합하지 않게 설계하며, 로그 출력 순서만으로 정확히 한 번 실행을 판단하지 않는다.

### 4.2 TCP 문자열 Echo

- 11.05 선택: 기존 게임을 클라이언트로 사용하고, 같은 솔루션의 `Server/Server.vcxproj`를 별도 콘솔 서버로 실행. 로컬 PC에서 문자열 왕복.
- Winsock 초기화·종료, 연결 대기·연결 요청, 송수신·소켓 정리를 직접 구현.
- 줄바꿈 또는 길이 헤더를 비교하고 메시지 경계 정책 선택. recv 한 번을 메시지 하나로 가정하지 않음.
- 부분 수신·연속 메시지·부분 송신, 연결 실패·상대 종료 처리.
- 수신 전용 스레드 사용 시 입력 스레드와의 공유 상태·종료 절차 명시. 오래 대기하는 recv를 기존 Job Pool에 넣지 않음.
- 수신 대기를 끝내는 API·절차와 소켓 소유자를 결정하고 정상 종료 후 join 확인.

11.05 후속 계획: 장기 수신 루프 대신 시작 시 한 번 끝나는 Echo 작업을 기존 Job Queue에 제출. 전용 테스트 스레드는 추가하지 않음. JSON Job을 먼저 제출하며 현재 `Start(1)`에서는 순차 실행. Job 내부 지역 소켓 사용, 연결·송수신 대기 제한을 설계한 뒤 적용. JobSystem 종료·join 후 Winsock 정리. 서버는 수신 바이트를 그대로 응답하고, 첫 클라이언트 검증은 보낸 길이만큼 응답을 누적해 비교. 일반 메시지 경계 정책 구현과 구분.

### 4.3 UDP 위치 값 Echo

- 기존 게임 클라이언트와 별도 콘솔 서버에서 순서 번호·X/Y 좌표를 포함한 데이터그램 왕복.
- 11.05 후속 계획: 고정 좌표 왕복 이후 메인 스레드에서 플레이어 위치를 복사해 유한한 Job에 값으로 전달. Worker가 Player 객체를 직접 읽지 않음. 응답은 검증용으로만 사용.
- 이번 완료 범위는 좌표 값 Echo까지. 실제 게임 위치 연결·다른 사용자 중계는 추가하지 않음.
- 메시지 형식·크기·좌표 유효성 검사. C++ 구조체 메모리를 전송할 경우 패딩·바이트 순서·표현 형식을 검토하고 포맷 명시.
- 응답 없음에 대한 대기 종료·프로그램 종료 처리, 오래된 순서 번호 처리 기준 마련.
- 로컬에서 자연 유실을 기대하지 않음. 필요하면 의도적 누락·순서 변경을 별도 실험으로 표시.
- 재전송·신뢰성 계층은 구현하지 않고 TCP와의 동작 차이를 설명하는 데 집중.

### 4.4 크래시 덤프 기본 분석

- 별도 작은 재현 프로그램에서 접근 위반 사례 하나를 사용자가 직접 작성.
- 처음에는 Debug 빌드와 Visual Studio의 힙 포함 미니덤프로 수집·열기·분석 실습.
- 크래시 당시 EXE·PDB·관련 소스 보존. 프로그램 종료 후 덤프에서 예외·호출 스택·스레드·인자 확인.
- 오류 발생 위치와 잘못된 상태가 생긴 경로를 구분해 수정하고 같은 조건으로 재검증.
- 시간이 남으면 ProcDump로 디버거 없이 실행한 프로그램의 처리되지 않은 예외 수집.
- 게임에 의도적 오류나 자동 덤프 수집기를 추가하지 않음. 덤프에서 확인되지 않는 상태는 추정으로 구분.

기본 합계: 집중 190분(3시간 10분), 휴식 20분, 총 210분(3시간 30분). 환경 구성이나 디버깅이 길어지면 추가 30~60분이 필요할 수 있으나, 이를 자동으로 오늘 일정에 더하지 않고 남은 작업을 수요일의 잔여 시간에 배치한다.

### 5.2 오늘 범위와 이월 기준

- 오늘 기본 목표는 현재 로딩 경로 이해와 Worker 1/2개·Job 10개의 기본 분배·예외·종료를 직접 확인하는 것. 과거 테스트 결과를 이번 결과로 대체하지 않음.
- 검증 환경 구성에서 오래 막히면 현재 게임의 디버거 추적과 가능한 실행 검증까지 기록하고 미완료 실험은 이월. 코드는 사용자가 작성하고 Codex는 API·설계·리뷰를 지원.
- Worker 4개·Job 100/1000개, 다중 생산자와 Submit/Stop의 의도적인 경합 검증은 추가 30~60분 후보. 오늘 기본 검증과 설명을 밀어내면서 수행하지 않음.
- TCP 구현은 내일의 기본 작업으로 배정. 오늘의 기본 합계에는 포함하지 않음.
- PNG 병렬 로딩은 오늘 필수·예정 구현에서 제외. 기본 준비와 검증·설명 이후 여유가 생겼을 때만 별도 선택. 책임 분리부터 실패·종료 검증까지 사용자 직접 진행 시 추가 3~5시간 추정으로 보고 짧은 남는 시간에 완료를 전제하지 않음.
- 기능 추가는 11.05에 마감. 작업이 길어지면 PNG와 부가 실험부터 줄이고 설명·검증 시간을 확보. 미완료 항목을 완료로 표시하거나 검증을 생략해 일정을 맞추지 않음.

## 6. 프로젝트 이해와 설명 연습

| 주제 | 코드에서 확인할 내용 |
| --- | --- |
| 소유권·수명 | GameWorld의 unique_ptr, 비소유 참조, Pool 재사용·Generation의 의미 |
| 전투 | 입력 → FSM·Animator → Physics → 충돌·피해, 공격 유효 프레임·중복 명중 방지 |
| 렌더링 | RenderInfo → Queue·Batch → Dynamic Buffer → DrawIndexed, Device·Context 차이 |
| 성능 | Draw Call·Render CPU·GPU 시간 구분, 측정 조건과 남은 비용 |
| C++ | RAII·이동·가상 소멸자·컨테이너 무효화·람다 캡처 |
| 동시성 | 공유 데이터, 데이터 레이스·교착, mutex·atomic·조건 변수, 종료·결과 전달 |
| 네트워크·디버깅 | TCP/UDP 데이터 단위·오류·종료, 덤프·심볼·분석 근거 |

하루 한 번 구현한 내용을 코드의 구체적 위치와 연결해 본인의 말로 설명한다. 프로젝트 소개·직접 해결한 문제·검증·한계 순서로 3분 안팎의 설명부터 연습한다.

기존 Sprite Batch는 Draw Call 감소와 Render CPU 증가가 함께 기록되어 있다. 이 결과를 속도 향상으로 묶지 않는다. 기존 자동 검증 204개·WARP 출력 확인도 이번 실행이나 실제 키보드 플레이 확인과 구분한다.

## 7. 완료 기록과 남길 근거

각 작업은 문제 / AI 지원 / 사용자 판단 / 실제 변경 / 검증 / 결과 / 한계 순서로 사용자와 함께 기록한다. 코드가 바뀌면 파일 경로·역할·소유권·새 개념을 문서에 반영하고 실제 작성·검증 주체를 구분한다.

- [ ] 제출 버전과 현재 버전의 핵심 흐름·AI 지원 범위 설명
- [ ] Thread Pool 계약·작업 분배·실패·종료 검증
- [ ] TCP 기본 Echo·메시지 경계·연결 실패·종료
- [ ] UDP 기본 위치 값 Echo·데이터 검사·응답 없음·종료
- [ ] 덤프 수집·종료 후 분석·원인 수정·재검증
- [ ] 실제 플레이·시연 확인과 미완료 항목 정리

체크는 실제 수행 근거가 있을 때만 변경한다. 성능 수치는 빌드 구성·Worker 수·이미지 목록·측정 구간·반복 조건과 함께 남긴다. 이미 있는 수치·과거 검증 기록은 보존한다.

## 8. 여유 작업: PNG 읽기·디코딩의 Thread Pool 적용

기본 준비가 완료되고 시간 여유가 있을 때만 진행한다. 미착수 상태여도 이번 기본 완료 범위의 누락으로 간주하지 않는다.

- [ ] 선택 작업: PNG 디코딩 분리·Job 연결·실패·종료·측정

방향: 이미지별 CPU 읽기·디코딩은 Worker, Texture·SRV 생성과 `textures_` 등록은 메인 스레드. 최종 자료형·함수 경계·Worker 수·수집 정책은 사용자가 결정.

| 단계 | 사용자 작업 | 확인 기준 |
| --- | --- | --- |
| 기준선 | 변경 전 실행·로딩 조건 기록 | 구성·이미지 목록·측정 구간 명시 |
| 책임 분리 | `LoadTextrue`의 디코딩과 GPU 생성 분리 | 우선 단일 스레드에서 기존 화면 유지 |
| 결과 소유권 | 이미지 ID·크기·픽셀 데이터의 소유·해제 설계 | 텍스처 생성까지 버퍼 유지, 실패·종료 시 회수 |
| Job 연결 | 기존 `std::function<void()>`와 promise/future 계약 활용 검토 | Worker가 ResourceManager의 공유 map·게임 상태·Context를 직접 변경하지 않음 |
| 로딩 단계 | JSON 대기 → PNG 대기 → 게임 초기화 | 완료된 future 재사용 방지, 메시지 처리·로딩 화면 유지 |
| 검증·비교 | 순차 처리와 Worker 1/2/4개 비교 | 전체 로딩과 CPU 디코딩 구간 구분, 개선 여부는 실측 후 판단 |

주의 사항:

- 현재 stb_image v2.30의 알 수 없는 필수 PNG 청크 오류 경로에 공유 static 오류 문자열이 존재. 정상 파일뿐 아니라 실패 경로의 동시 접근도 검토.
- `StbImage.cpp`에서 `STBI_NO_FAILURE_STRINGS`로 해당 오류 문자열 경로를 제외하는 방법을 후보로 검토. 상세 라이브러리 오류 문자열을 쓰지 않는 대신 파일 경로를 포함한 오류를 전달할지 사용자가 결정.
- Worker에 경로·결과 채널을 안전하게 전달하고 Job보다 짧게 사는 지역 변수의 참조 캡처를 피함.
- 일부 Submit 거부·디코딩 실패 후에도 이미 접수된 Job의 수명과 결과 버퍼 보장. Worker에서 다른 Job 완료를 기다리는 구조는 피함.
- 로딩 중 종료는 강제 취소가 아닌 기존 Stop·join 계약을 기준으로 설계. 완료 결과를 모을 때의 최대 메모리도 확인.
- 단순화를 위해 마지막 GPU 리소스 생성을 한 번에 수행하면 해당 구간은 메인 스레드를 점유한다는 한계 기록.
- 새 파일이 필요하면 사용자가 `.vcxproj`·`.filters`에 직접 등록. 불필요한 전체 로더 재설계는 피함.
