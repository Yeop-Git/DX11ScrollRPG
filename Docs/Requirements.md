# DX11ScrollRPG 요구사항 명세

작성 기준: 2026.09.26. 일정은 [작업 계획](SprintWorkPlan.md)을 참조한다.

## 1. 목적과 상태 표기

직접 구현한 Win32 / DX11 게임을 기반으로 공격 확장, 객체 참조 안전성, 멀티스레드 실행, 네트워크 동기화를 학습하고 검증 가능한 포트폴리오로 정리한다. 실제 필요와 학습 목적을 구분하고, 기능 개수뿐 아니라 설계 선택·소유권·실패 처리·검증 결과를 설명할 수 있어야 한다.

- **구현·검증됨:** 현재 코드와 실행 기록이 있음. 게임에 연결됐는지는 별도 표시.
- **요구:** 사용자 요청 또는 기존 Sprint 목표. 구현 완료를 뜻하지 않음.
- **제안:** 구현을 위해 제시한 기본안. 사용자 선택 전에는 확정 정책이 아님.
- **후속:** 구현 대상이지만 10.02까지의 기본 완료 범위 밖.

현재 Thread Pool은 시작 시 JSON 파일 로딩에 연결됐다. 성장·스킬·Handle·HUD는 [구현 기록](CombatImplementation.md)의 자동 검증까지 완료. 네트워크 확장은 미구현 상태다. 기본 공격과 기존 Pool, 렌더링 기능은 기존 동작을 보존한다.

## 2. 실행 주체와 소유권

| ID | 요구사항 | 확인 기준 |
| --- | --- | --- |
| ARCH-01 | 클라이언트 윈도우 메시지·입력·게임 상태 갱신·DX11 Immediate Context 접근은 메인 스레드에서 수행 | Worker에서 해당 상태/API를 직접 수정·호출하는 경로가 없음 |
| ARCH-02 | JobSystem Worker는 독립 입력 데이터로 계산·파일 처리하고, 게임 적용용 결과를 전달 | Worker가 Player / Monster / GameWorld를 비소유 포인터로 캡처해 직접 변경하지 않음 |
| ARCH-03 | World 객체의 실제 수명 소유는 GameWorld의 unique_ptr 기반 구조를 유지 | Pool·Handle·Lookup은 소유자와 비소유 참조 역할이 명확함 |
| ARCH-04 | IOCP의 OS 완료 Queue와 일반 함수 Job Queue를 구분 | 네트워크 완료 처리 경로와 JSON 작업 경로를 각각 설명 가능 |
| ARCH-05 | 향후 완료 결과/게임 명령 Queue는 메인 스레드가 정해진 프레임 구간에서 처리 | enqueue와 처리 시점, 오류·취소·월드 전환 정책이 문서화됨 |

메인 스레드용 결과/명령 Queue에는 자체 Worker가 필요 없다. `JobSystem.Start(1)`은 별도 Worker 하나를 만드는 것이므로 클라이언트 메인 스레드에서 실행하는 것과 다르다. 초기 결과 Queue는 mutex 기반으로 충분하며 Lock-free MPSC를 요구하지 않는다.

## 3. Thread Pool / Job Queue

상태: **구현 및 시작 시 JSON 로딩에 연결됨.** 실제 계약과 검증 결과는 [ThreadPool.md](ThreadPool.md)에 기록한다.

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| JOB-01 | 고정 Worker들이 단일 `std::function<void()>` Queue를 공유 | Worker 1 / 2 / 4 × Job 10 / 100 / 1000의 작업별 실행 횟수가 정확히 1 |
| JOB-02 | Queue·접수 상태·실패 집계는 mutex로 보호하고 조건부 wait 사용 | 동시 제출 시 누락·중복 없음. 작업 실행은 잠금 밖에서 수행 |
| JOB-03 | Start / Stop / 파괴는 생성 스레드에서 수행 | 0 Worker·중복 시작·빈 작업·미시작/종료 중 제출·잘못된 스레드 호출의 정책 확인 |
| JOB-04 | Stop은 새 작업을 막고 접수된 작업을 모두 처리 후 join | 실행 중·대기 중 작업이 있어도 완료 후 반환. 반복 Stop·재시작·소멸자 종료 확인 |
| JOB-05 | Job 예외로 Worker가 유실되지 않도록 실패 집계 | 예외 후 후속 작업 실행, 실패 횟수 확인. 예외 상세·재시도는 범위 밖 |
| JOB-06 | 작업이 캡처한 데이터의 수명은 호출자가 보장 | 참조 대상과 JobSystem 파괴 순서 명시. 외부 제출자는 JobSystem 파괴 전에 접근 중단 |

제한: 무한 대기 Job 강제 취소, Queue 용량 제한, 범용 future 반환 Submit, 템플릿 인자 포장, 작업 의존성 그래프는 현재 구현에 없다. Worker 부분 생성 실패 회수 경로는 구현됐으나 실패 주입 검증은 미실행이다.

27·28일 통합 작업의 코드 연결·정책 제안·C-01~22 수용 기준은 [통합 공격 구현 계획](CombatImplementationPlan.md)에 명세. 아래 확정 요구를 유지하며 세부 동작·수치는 해당 문서의 추천안으로 구분.

### 스킬별 제안안

| 슬롯 | 에셋 후보 | 동작 제안 | 필요한 판정 |
| --- | --- | --- | --- |
| Q | Fire_Ball | 전방 직선 발사, 첫 적 명중 후 반환 | 단일 명중, 최대 수명/거리, 좌우 방향 |

| E | Earth_Spike | 전방 지면에 잠깐 생성되는 범위 공격 | 지면 배치, 유효 프레임, 대상별 피해 횟수 |
| R | Tornado | 큰 회오리의 느린 전진과 주기적 피해 | 대상별 피해 간격, 최대 수명, 종료 연출 |

이름·공격 동작은 추천안이며 최종 선택 전이다. 피해량, 투사체 속도·크기·거리·수명, 애니메이션 속도와 R 피해 간격은 미정이다. R 끌어당기기·띄우기는 기본 범위에 없다.

## 5. Pool / Handle / Lookup / Generation

상태: **구현·자동 검증, 포트폴리오 학습·확장 목적.** 실제 메모리 삭제를 일부러 추가하지 않는다.

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| LIFE-01 | Projectile과 HitEffect는 Pool로 대여·반환 | 사용 회차 종료 후 비활성화 및 상태 초기화, 중복 반환 방지 |
| LIFE-02 | Handle은 객체의 주소·소유권이 아닌 현재 사용 회차의 비소유 식별자 | 외부 조회 경로가 저장소를 통해 유효성을 검증 |
| LIFE-03 | Lookup은 인덱스 범위·사용 여부·Generation 확인 후 접근 허용 | 기본/잘못된 Handle·반환된 Handle 조회 실패 |
| LIFE-04 | 슬롯 재사용 시 이전 Handle이 새 객체를 식별하지 못함 | A 반환 → 같은 슬롯 B 대여 → A Handle 실패, B Handle 성공 |
| LIFE-05 | 월드 Reset 이후에도 과거 Handle이 살아나지 않음 | 슬롯/세대 초기화만으로 오래된 값이 새 객체와 우연히 일치하지 않는 정책 검증 |
| LIFE-06 | 기존 Monster / Item Pool을 일괄 전환하지 않음 | 적용 대상과 미적용 참조 목록 문서화 |
| LIFE-07 | Pool 객체의 위치·속도·수명·애니메이션·피격 이력 초기화 | 재사용 시 이전 회차의 결과가 남지 않음 |

Generation 증가 시점, 번호 범위 초과, 저장소 식별 범위, Pool 고갈 정책은 설계 단계에서 결정한다. Lookup으로 얻은 raw pointer의 사용 기간을 제한한다. Handle은 동시 삭제 중의 수명이나 스레드 안전성을 보장하지 않는다. 이번 검증 대상은 Pool의 논리적 수명이며, 실제 객체 삭제의 등록 해제·메모리 회수 검증은 별도 후속이다.

| DATA-02 | Animator의 현재 프레임·누적 시간·완료 상태와 FSM 판단은 런타임 코드에 유지 | JSON에 실행 중 상태를 혼합하지 않음 |
| DATA-03 | 먼저 동기 로더로 파싱·검증 계약 확보 | 파일 없음·문법 오류·필수 키 누락·타입 오류·비정상 수치·미등록 스프라이트 처리 확인 |
| DATA-04 | 같은 로더를 JobSystem에서 실행 | 메인 스레드는 결과 준비 전 로딩 상태로 진행하며 Worker에서 게임 객체를 직접 수정하지 않음 |
| DATA-05 | 성공 데이터와 오류 정보를 소유한 완료 결과 전달 | 메인 스레드가 안전한 시점에만 적용. 실패 시 부분 설정이 적용되지 않음 |
| DATA-06 | 현재는 시작 로딩 1회와 종료 중 join 보장 | 재요청·핫 리로드·월드 전환은 후속. 도입 시 요청 식별·취소·오래된 결과 제외 정책을 추가 |
| DATA-07 | 향후 맵 ID·맵 배치·Spawn 설정으로 확장 가능하도록 책임 분리 | JSON 읽기/파싱과 World 적용 코드가 분리됨. 맵 전체 스키마 구현은 장기 후속 |

공통 작업은 std::function<void()>를 유지한다. nlohmann/json 3.12.0으로 GameData schemaVersion 3·Stat schemaVersion 1 파일을 읽고, 로더의 promise/future로 성공 데이터 또는 예외를 전달한다. 필수 설정 실패는 파일 경로와 오류를 표시하고 시작을 중단한다. Application이 불변 GameData를 World보다 오래 소유하며, 마지막 멤버인 JobSystem이 먼저 파괴되어 Worker를 join한다. 파일마다 Stop하지 않는다. PNG 디코딩과 D3D 생성은 현재 메인 스레드다.

## 8. IOCP와 게임 네트워크

상태: 날짜 미정의 후속 작업. 27·28일 통합 공격 구현 범위에서 제외. 기존 네트워크 요구는 보존하며 IOCP 재개 후 상세 설계 진행.

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| NET-01 | Winsock, Listen/Accept, IOCP 등록 및 Worker 완료 처리 | Client Echo가 비동기 Receive/Send로 왕복 |
| NET-02 | Session / OVERLAPPED / 버퍼 수명 분리·보장 | Disconnect와 서버 종료 중 Pending I/O가 사용하는 메모리를 조기 해제하지 않음 |
| NET-03 | 누적 Receive Buffer와 길이 기반 Packet Framing | 헤더·본문 분할, 여러 패킷 병합, 잘못된/최대 크기 처리 |
| NET-04 | 송신 순서 및 부분 완료 처리 | 일부 바이트 완료 후 남은 데이터 처리, 송신 중 Disconnect에서 버퍼 재사용 오류 없음 |
| NET-05 | 두 Client의 식별·Spawn·Move·Despawn | 서로의 생성·이동·정상/강제 종료 반영. 없는 ID·중복 처리 정책 명시 |
| NET-06 | Client 수신 결과는 메인 스레드에서 게임 상태에 반영 | 네트워크 스레드가 GameWorld 목록·렌더 객체를 직접 변경하지 않음 |
| NET-07 | Remote Snapshot Buffer와 보간 | 정상 간격·불규칙 도착·버퍼 부족 시 동작 정의. 보간 지연 기록 |
| NET-08 | 최종 이동은 서버가 입력으로 계산 | 위치 직접 신뢰 방식에서 입력 sequence/방향/점프 요청으로 전환, 서버 결과 전파 |

IOCP Worker는 GetQueuedCompletionStatus로 OS 완료 Queue를 기다린다. 이것은 JobSystem의 condition_variable 대기와 별도다. 서버 월드 상태를 전담 로직 스레드/틱에서 처리할지, Session별 순차 실행을 둘지는 비교·선택할 설계다. 모든 스레드가 같은 상태를 임의로 수정하는 구조는 피한다. 특정 스레드에서의 실행과 단순한 동시 실행 금지를 구분한다.

게임의 QWER, Monster, Item 네트워크 동기화는 이번 범위에 없다. Client Prediction / Reconciliation도 제외하므로 로컬 입력 지연을 숨기거나 해결됐다고 기록하지 않는다.

## 10. 공통 품질 기준

| ID | 요구사항 | 확인 기준 |
| --- | --- | --- |
| QA-01 | 최소 변경과 기존 스타일 유지 | 변경 파일·호출 흐름·소유권·도입 개념 설명, 새 코드에 목적을 설명하는 주석 |
| QA-02 | 실패·수명 경계 검증 | 기능별 정상·실패 테스트와 미실행 항목 구분 |
| QA-03 | 검증 결과를 실제 증거로 기록 | 빌드 구성·실행 결과·측정 조건 명시. 자동 테스트와 사용자 육안 확인 구분 |
| QA-04 | 성능 최적화는 수치로 확인 | 같은 조건의 Before/After. 임의의 FPS 향상 목표나 미측정 개선 주장 없음 |
| QA-05 | 새 파일을 VS 프로젝트/필터에 등록 | 사용자가 솔루션에서 코드와 테스트 위치를 확인 가능 |

순차 Queue를 사용해도 모든 Deadlock이 사라지는 것은 아니다. Queue 밖의 접근, 작업 간 순환 대기, 메인 스레드와 Worker의 상호 대기를 검토한다. 하나의 긴 작업이 뒤의 작업을 지연시키는 한계와 Queue 누적에 대한 처리 예산/고갈 정책도 실제 적용 단계에서 정의한다.
